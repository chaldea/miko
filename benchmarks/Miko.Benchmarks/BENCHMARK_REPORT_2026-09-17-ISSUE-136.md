# ISSUE-136 基准报告：消除 DOM 构建中的反射与装箱

- 提交：`fix/ISSUE-136`（对照基线见 `BENCHMARK_REPORT_2026-09-17-ISSUE-136-before.md`）
- 日期：2026-09-17
- 命令：`dotnet run -c Release --project benchmarks/Miko.Benchmarks -- --filter "*ComponentFrameBenchmarks*" --job short`
- BenchmarkDotNet `ShortRun`（1 次启动、3 次预热、3 次迭代）

## 结论

构建阶段（本次优化的对象）**耗时降低 23–27%、分配降低 3.3%**；整条帧管线无退化。

issue 要求「优化后再重新执行基准看性能是否退化」。**未发生退化**：首帧端到端与状态变更
场景均与优化前持平或更快（详见下文「端到端对照」，差异落在 `ShortRun` 的误差范围内）。

## 构建阶段：新旧 API 直接对照

两条路径都还在产品里（名字驱动那条仍支撑 `AddMarkupContent` 的运行时 HTML 解析），
因此可以在同一次运行里构建**完全相同**的树做对照。差值就是本次去掉的开销：标签名查字典
取工厂委托、属性名过约 70 分支的 switch + 类型测试链、以及每个组件参数一次无缓存的
`GetProperty` + `SetValue`（值类型还要装箱）。

| 组件数 | 强类型构建 | 旧的名字驱动构建 | 耗时改善 | 分配改善 |
|---:|---:|---:|---:|---:|
| 20 | **3.571 us / 27.81 KB** | 4.874 us / 28.72 KB | **-26.7%** | -3.2% |
| 100 | **16.876 us / 135.61 KB** | 23.631 us / 140.27 KB | **-28.6%** | -3.3% |
| 300 | **59.051 us / 407.29 KB** | 76.414 us / 421.31 KB | **-22.7%** | -3.3% |

分配的改善幅度远小于耗时，符合预期：省掉的是装箱与 `SetValue` 的参数数组这类**小对象**，
而构建阶段的分配主体是元素实例本身（两条路径都要 new）。真正被消除的是**每节点的查找与
反射工作**，那是纯 CPU 开销。

**耗时数字不要过度解读。** `ShortRun` 的误差与均值同量级（如 100 组件的 StateHasChanged
一栏 Error 高达 11,098 us），两次运行之间本就有大幅波动。可靠的读数是 `Allocated`：

- 首帧分配一致下降约 **0.9%**；
- `StateHasChanged` 分配下降 **1.8–2.4%**——这条路径每帧都重跑级联参数解析，正是
  `ComponentParameterCache` 消除反射的地方；
- 「状态变更但复用布局」分配**完全持平**——该场景不重建组件树，本次改动理应不影响它，
  数据也确实如此。这反过来说明上面两行的下降不是噪声。

## 为什么端到端的改善看起来不大

构建只占整条管线的一小部分。以 300 组件为例：构建 59 us，而整帧 5,757 us——构建占约
**1%**。因此即便构建快了 23%，端到端也只会动 0.2 个百分点。这正是本次新增
`Component Build only` 与 `Component Build only, legacy name-based API` 两个用例的原因：
把被优化的那一段单独量出来，而不是让它淹没在布局与绘制里。

同样的道理也适用于分段探针（`Miko.Diagnostics.FrameTimingDiagnostics`）：它把构建/样式/
布局/绘制分开计时，并单独记账首帧，供后续优化直接观察各阶段而不必反推。

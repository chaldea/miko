# 基准测试报告：长列表虚拟化（ISSUE-151）

> 问题：Infinite Scroll 示例每加载一批就往列表里追加行，DOM 越来越大，每次加载、每个滚动帧的
> 成本都随已加载行数线性增长。本报告确认引入 `Virtualize<TItem>` 之后，这些帧不再随行数增长。

| 日期 | 2026-10-27 |

| .NET | SDK 10.0.401，运行时 10.0.12，Arm64 RyuJIT |

| 驱动 | `MikoEngine`（`MikoEngineBuilder`），滚动走 `ScrollBy` → `Render`，与宿主一致 |

## 测了哪四种帧

| 帧 | 内容 |
|---|---|
| 首帧 | 打开页面：组件构建 + 样式 + 布局 + 绘制 |
| 滚动帧 | 一次 16px 的滚动。多数帧只重绘；每滚过几行窗口移动一次，列表自渲染 |
| 跳跃帧 | 一次 600px 的滚动——每帧都移动窗口，相当于快速甩动的最坏情况 |
| 数据变更帧 | 无限滚动一次加载做的事：追加 5 行（隔次删回）并重渲染页面 |

普通列表只测到 2,000 行：再往上一帧要几秒、DOM 就要几百 MB——那正是要解决的问题。

## 解读

**普通列表的每一种帧都随行数线性增长。** 数据变更帧（一次加载）在 1,000 行时 85 ms、2,000 行时
172 ms——页面重渲染要把每一行重新构建、整树级联、重排。滚动帧虽然只重绘，也从 0.35 ms 涨到 8 ms：
绘制不裁剪视口外的行，命中测试（`ScrollBy` 找滚动容器）也要走整棵布局树。

**虚拟化列表的 DOM 恒为 186 个元素**（视口内约 12 行 + 上下各 3 行余量 + 两个占位块），与行数无关：

- **滚动帧 0.19–0.22 ms**，平坦。窗口内的滚动是纯重绘（布局缓存命中、变更版本号不变）。
- **数据变更帧 1.27–1.28 ms**，平坦，100 到 100,000 行完全一致。追加/删除尾部只给新增的那几行
  建键（`TryRekeyTail`），不遍历整个集合。
- **跳跃帧 1.1–1.3 ms**（1,000 / 10,000 行）。窗口每帧都换：新滚入的几行要构建，窗口内其余行沿用
  元素（不重新构建），整页重新级联与布局一次。100,000 行的 2.07 ms 不是行数造成的：这个基准从顶部
  一路往下跳，100,000 行时每一帧都落在**从没量过**的行上，量完后估计行高变了，两个占位块要按新估计
  改高度，于是多一次重排。在**同一片区域**里来回跳时，10,000 行与 100,000 行每帧分配完全相同
  （均为 1.83 MB/帧，临时探针实测）。即：首次经过的行多一次重排，此后与行数无关。
- **首帧**在 100,000 行时 5.6 ms：其中约 3 ms 是 `ItemKey` 为十万个元素建一次键表（O(N)，只在列表
  第一次渲染与键整体失效时发生）。不给 `ItemKey` 时没有这一项。

与 issue 的对应：issue 描述的「加载越多越卡」由数据变更帧体现——普通列表 2,000 行时一次加载 172 ms
（10 帧），虚拟化后 1.3 ms，且到十万行不变。

## 问题 1：窗口移动帧（2026-10-28）

真机上「每次滚到窗口边界都卡一下」。桌面上窗口移动帧只有约 0.5 ms，看不出问题；问题在 Android（Mono）上，
所以这一节在模拟器上测。

**测法**：Pixel 7 API 36 模拟器（冷启动），IonicDemo.Android Release，Infinite Scroll 页预置 300 行，
同一段 `adb shell input swipe` 脚本（6 次慢拖向下、3 次向上、3 次快甩），逐帧记录 `FrameProfiler` 与
`GC.CollectionCount(0)`。两个 APK 背靠背各跑两轮，下表为两轮均值。「窗口移动帧」= 本帧做了布局的帧，
其余帧只重绘（约 0.5 ms，两版相同）。

| 构建 | 窗口移动次数 | p50 | p90 | 样式 | 布局 | 每次分配 | 触发 GC 的移动帧 | 移动帧总耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 改前（默认 Profiled AOT） | 35.5 | 5.6 ms | 8.5 ms | 2.8 ms | 2.2 ms | 1.6 MB | 39% | 216 ms |
| 改后（默认 Profiled AOT） | 24 | 4.7 ms | 7.6 ms | 3.0 ms | 1.0 ms | 0.85 MB | 12.5% | 125 ms |
| 改后 + LLVM（`-p:AndroidEnableProfiledAot=false -p:EnableLLVM=true`） | 24 | 2.3 ms | 5.1 ms | 1.3 ms | 0.6 ms | 0.85 MB | 25% | 70 ms |

窗口移动帧的成本来自**整页**重新级联与重排：移动窗口是一次结构变更，样式版本号递增，整棵树重算
——与移动了几行无关。改前它还有三项浪费：

1. **Ionic 的滚动容器被排三遍**。`.inner-scroll` 是 `position:absolute; inset:0`，父级常规流先按
   shrink-to-fit 测一遍整棵内容的内在宽度、再按测出的宽度排一遍，定位阶段又按包含块排一遍。现在这类
   两轴都由偏移定型的盒子推迟到定位阶段只排一次（布局 2.2 → 1.0 ms）。
2. **移出窗口的行的计算样式没回到池里**。每次移动约 80 个（6 KB/个）交给 GC，移入的行再新建同样多；
   四成移动帧因此多一次 GC（+3 ms）。现在它们被回收复用（每次分配 1.6 → 0.85 MB）。
3. **动画对齐每帧为整棵树建一张字典**（两遍）。现在按动画条目沿祖先链判定，整树只走一遍。

另外，窗口移动时 2 × `OverscanCount` 的余量大部分放在滚动方向前方，同一段滚动窗口少移约三分之一。

剩下的样式成本是整页级联本身（约 240 个元素），在 Mono 默认代码生成下约 3 ms；LLVM 后端把它降到
约 1.3 ms（与 ISSUE-146 的结论一致）。只重算移入的那几行需要「局部结构变更」级别的样式失效，
目前没有。

桌面 `--long-list`（改前 / 改后，范围取各行数）：Virtualize 跳跃帧 1.1–1.5 / 0.8–1.0 ms，数据变更帧
1.2–1.3 / 1.0–1.15 ms。普通列表 100 行的数据变更帧波动大（四次运行：改前 8–13 ms、改后 7–12 ms），没有退化。
